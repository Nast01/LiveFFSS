# Contrat de l'API FFSS — faits vérifiés

> Section « API contract » du CLAUDE.md de la v1 (`live_ffss/CLAUDE.md`), reprise telle quelle le 2026-10-17. Ce sont des comportements constatés sur de vraies réponses du serveur : là où ils contredisent `FFSS_API.md`, ils gagnent. Les noms de fichiers cités sont ceux de la v1.


- **`docs/FFSS_API.md` est la référence de surface de l'API** — la doc officielle FFSS restructurée : conventions (enveloppe `success`, erreurs toujours en HTTP 200, temps en centièmes, pagination DataTables), modèles partagés, hiérarchie `Evenement → Epreuve/Deroulement/Reunion → Creneau → Course → Place`, et le catalogue complet des routes par domaine. **C'est là qu'on regarde d'abord pour savoir ce que l'API permet** avant de proposer une feature ou d'inventer un appel. Deux réserves : elle décrit ce que la doc annonce, pas ce que le serveur fait vraiment — là où elle contredit les points ci-dessous, **ces points gagnent**, ils sont vérifiés sur de vraies réponses (les routes cassées listées dans Known gaps y figurent comme fonctionnelles, et elle ne dit pas que seule l'auth par paramètre `token` est honorée) ; et sa §5 énumère ses propres incohérences — la lire avant de s'appuyer sur un champ douteux.
- Deux environnements : production `https://ffss.fr/api/v1.0/`, développement `https://site.ffss.io/api/v1.0/`. `AppEnvironment` (`core/config/app_environment.dart`) les porte ; `AppConfig.fromEnv()` en choisit un au démarrage. **Le développement n'est joignable qu'en build debug** — hors debug `AppEnvironment.resolve` renvoie la production sans condition, même si un choix « développement » traîne dans le secure storage. Path templates (with `:id` placeholders) and the `replacePath(path, params)` helper live in `core/config/app_config.dart` (`ApiEndpoints`). A duplicate `ApiConstants` used to sit in `core/const/api_const.dart`; it was dead and has been deleted — don't reintroduce it.
- `HttpClient.get/post` returns the **full decoded body** as `Map<String, dynamic>`. Datasources extract `body['data']` themselves — `me` endpoint has fields at both top-level and nested under `data`, so unwrapping in HttpClient would lose info.
- **UTF-8 decoding:** HttpClient decodes `utf8.decode(response.bodyBytes)`, NOT `response.body`. FFSS omits the charset in the response `Content-Type`, so `http` would fall back to latin-1 and mangle accents (`é` → `Ã©`). Never switch back to `response.body`.
- **Auth: the `token` query parameter, from `TokenStorage`.** FFSS ignores `Authorization: Bearer` — `GET /me` carrying only the header answers `"Utilisateur Anonyme"`, identical to sending no credentials, while `GET /me?token=…` returns the real account. Reads still serve their public data anonymously, so a missing token shows up not as a 401 but as a write failing with `Invalid Token`. `HttpClient._buildUri` injects it on every request. The Bearer header is still sent alongside; it is inert but harmless. **Do not "fix" this back to header-only auth** — this file used to mandate exactly that, and it silently left the app unauthenticated. The token does land in server logs and proxies; the API leaves no alternative.
- **A dead token shows up as `403 {"error":"Forbiden","message":"Invalid token"}` on writes — never a 401 — while reads with that same dead token are served anonymously as a plain 200.** Tokens also die well before the `expiration` date `requestToken` returns, so that date proves nothing. `HttpClient` treats a 403 whose message says `invalid token` as a session failure (logout + `/login`); other 403s stay `ApiException`, since a genuine refusal must not sign anyone out.
- **`engagement` a trois valeurs, pas deux** (vérifié le 2026-09-03). Une place créée sans occupant part avec `'0'` ; la chaîne vide **libère** une place déjà occupée ; l'id de l'engagement l'assoit. `MeetingRemoteDataSource.submitLane` les porte dans un `String` requis, jamais un `int? entryId` nullable qui confondrait « pas d'engagement » et « libérer ». `MeetingRepository.createDefaultLanes` envoie `'0'`, `syncLanes` assoit chaque engagement par son id et écarte le surplus via `deleteLane`, jamais par un `engagement: ''` — **aucun chemin de code n'envoie `''` aujourd'hui.** La datasource l'accepte pour que la libération reste possible (le doc comment de `submitLane` le dit), mais rien ne l'appelle encore ; assorti à `withdrawAthlete` toujours `UnimplementedError`, ça marque un chemin non construit, pas perdu.
- **Le dossard d'un athlète, `Dossard`, arrive sur toute charge utile de forme athlète** — `competition/engagement` comme `evenement/:id/organismes` — et `AthleteDto` le décode partout (`orderNumber`). Aucun appel dédié n'est nécessaire : les six écrans qui montrent un athlète l'obtiennent avec lui.
- **`competition/evenement/:id/participants` existe mais n'est plus appelée, et ne doit pas l'être pour joindre un dossard : l'`Id` d'un athlète y est différent du sien dans `engagement`.** Vérifié le 2026-09-18 sur l'événement 1453 : Eli Sandbach est `Id: 663377` dans `participants` et `Id: 663374` dans `engagement`, même `idInvite: 9013`, même `Dossard: "329"`. Les deux numérotations se chevauchent, donc une jointure sur `Id` tombe juste par accident — elle l'a fait pour 12 athlètes sur une épreuve entière, ce qui est exactement ce qu'un tel bug donne à voir. Un `ParticipantService` bâti là-dessus a été écrit puis supprimé ; si un besoin futur exige `participants`, joindre sur `NumeroLicence` (ou `idLicencie`/`idInvite`), jamais sur `Id`.
- `competition/reunion/:id/delete` **fonctionne** — même forme que les autres suppressions (`token` + `id`, réponse `success`/`message`) — à la différence de `GET competition/reunion/creneau/:id/course`, toujours cassée (voir Known gaps).
- **`competition/reunion/creneau/:id/delete` sur un créneau qui porte encore des courses n'est pas vérifié.** Contrairement à `reunion/delete`, dont la cascade a été confirmée, rien ne documente ce que FFSS fait des courses d'un créneau supprimé : soit il les emporte avec lui (même comportement que `reunion/delete`), soit il les orpheline — des courses que ni cette app ni FFSS ne permettraient plus jamais d'atteindre. Ne pas appeler la route pour trancher : ce serait une écriture destructrice sur un serveur fédéral partagé.
- Success envelope: `success: true` (or absent). HttpClient throws `ApiException` on a refusal — **`false` ou la chaîne `"false"`, les deux formes que FFSS emploie selon la route** ; `"false"` est une chaîne non vide, donc véridique en Dart, et le tester par `== false` laissait passer un refus pour un succès. Puis `AuthException` on 401, `ApiException` with statusCode on 4xx/5xx, `NetworkException` on `SocketException`, `TimeoutException` **et `http.ClientException`** (ce que le web lève à la place de `SocketException`, qui n'y existe pas), `UnknownException` for anything else. **`AppException` rethrows pass through unchanged** — don't catch and re-wrap.
- **Un id d'écriture se lit avec `assignedId`, et une suppression avec `wasAccepted`** (`data/datasources/api_envelope.dart`). FFSS rend `id` tantôt entier, tantôt chaîne : les dix `submit*` le lisaient de quatre façons, dont six qui n'acceptaient que l'entier — un id servi en `"123"` faisait alors passer une création réussie pour un refus. Ne pas re-dérouler l'extraction à la main, et ne pas doubler le test d'enveloppe que `HttpClient` fait déjà.
- **La saison demandée se déduit de la date du jour** — `seasonLabel`/`seasonStart` (`core/utils/ffss_season.dart`), une saison FFSS courant du 1er octobre au 30 septembre. Elle était figée en constante, et remontait donc une saison révolue depuis le 1er octobre suivant. `CompetitionRepositoryImpl` prend une horloge injectable pour que ce calcul soit testable ; c'est son seul usage.
- **`visibility` est nullable, et nul veut dire « pas de filtre »** — ce qui n'est pas la même chose que `incoming` ou `passed`. Le paramètre traversait toute la chaîne sans jamais être envoyé ; l'accueil demandait `passed` tout en comptant afficher les compétitions à venir, donc il n'en demande plus aucune. Les deux noms de l'enum sont exactement ceux que l'API attend.
- Clés du secure storage préfixées par environnement : production `''`, développement `'dev_'`. Six clés sont cloisonnées (`token`, `user`, `favorite_competitions`, `last_viewed_competitions`, `race_attendance`, `programme_<id>`), trois restent globales (`language`, `api_environment`, `debug_http_log`). La règle unique est `AppEnvironment.owner(key)` — ne pas la dupliquer ailleurs. Le préfixe de production est vide, ce qui rend le cloisonnement rétro-compatible : ne pas lui en donner un.


## Programme, vérifié le 2026-10-17 sur la recette 1416

Constats faits sur de vraies réponses de la recette (`https://site.ffss.io/api/v1.0/`, compétition 1416). Extraits dans `live_ffss.v2/test/fixtures/recette_1416/`. Ils l'emportent sur `FFSS_API.md`.

- **`competition/:id/reunion` porte déjà la `partie` de chaque créneau d'épreuve**, mais sans son `deroulement`. Elle est `null` pour les créneaux sans épreuve (ouverture des portes, échauffement, pause, cérémonie).
- **Les places des listes sont vides** (`reunion` comme `creneau/:id`) : `Numero` et `id` seulement, `engagement`, `resultat` et `athletes` à `null`.
- **`competition/reunion/creneau/course/place/:id` rend la place complète**, avec `resultat.rangLabel` (« 5ème »), rang officiel **par catégorie**. **Sur une DQ, `rangLabel` porte le code de disqualification** (« 12 », `performanceLabel` « 12 - ») et `disqualificationCode` reste `null` (vérifié le 2026-10-17 sur la place 2903, course 490, recette 1416). Le résultat n'a **ni `complement`, ni code `Statut`**. La réponse porte aussi des données personnelles du licencié (e-mail, date de naissance, numéro de licence, dossard) que l'app ne lit pas et que les extraits de test ont retirées.
- **`competition/reunion/creneau/:id` ne porte pas la réunion** : `Id`, `Nom`, `Debut`, `Fin` (`HH:mm`), `courses` et `partie` avec le `deroulement` complet et toutes ses `parties`.
- **`competition/reunion/creneau/:id/course` échoue** : `success: false`, message « filterByCreneau() only accepts arguments of type … Creneau or Collection ».
- **Deux formes de déroulement.** Dans la liste `competition/:id/deroulement`, `Discipline` (objet) et `Genre` (`H`/`F`). Imbriqué dans une `partie` (`creneau/:id`), `discipline` et `genreLabel`. Même objet, clés différentes.
- **L'objet `serie` d'une course de `reunion` est réduit** : `id`, `nom`, `niveau`, `fullLabel`, **sans `Numero` ni `epreuve`**. Les courses d'une finale non générée ont `serie: null`.

## Connexion et résultats, vérifié le 2026-10-18 sur la recette (compte officiel de test)

- **`GET /me?token=…`** → `{success, message, label: "NOM Prénom", type: "licencie", data: {club, nom, numero, prenom, role}}` ; `data.role` vaut `user` pour un compte licencié.
- **`GET competition/evenement/:id/me?token=…`** → `{"data": {"roles": [...], ...}}`, avec un objet par rôle détenu : `licencie {id, nom, prenom}`, **`officiel {id, niveau, niveauLabel, principal}`** (ex. `niveau` « B », `niveauLabel` « B - Juge de virage/obstacles », `principal: false`), `referent_sportif [{id, label, sigle, nom}]`. Rôles observés : `public, licencie, officiel, referent_sportif` — **`referent_sportif` n'est pas dans la doc**. Sans jeton : `{"roles": ["public"]}`.
- **`TempsLive1..3` sont servis par `competition/resultat/:id` et `competition/serie/:id`** (résultats), **pas** par `course/place/:id`. `resultat/:id` porte `Id, Temps, tempsLabel, TempsLive1..3, Rang, Statut, statutLabel, complement, complementLabel, points, isValid, isDisqualifie, engagement, serie, Athletes, isRecord…` — de quoi reconstruire tous les champs de `resultat/submit`.
- **Écriture `POST competition/resultat/submit`, vérifiée le 2026-10-18 sur le résultat 572548 (série 94894, engagement 566311) :**
  - **Les paramètres passent dans l'adresse** (query string, comme le jeton), sans corps : un corps JSON répond **HTTP 500** sans message, même avec tous les champs. C'est ce que faisait la v1.
  - Réponse : `{"success":true,"message":"résultat enregistré","isRecord":false,"isCreation":false,"id":572548}`.
  - **Un `statut` omis n'est pas conservé** : il retombe à **3 (« F/DQ »)** et `isValid` passe à `false`. `temps`, `rang`, `tempsLiveN` et `complement` omis sont conservés. Après relecture, **toujours renvoyer `statut`, `complement` et `tempsLive1..3`** ; **`temps` et `rang` ne sont jamais envoyés** (omis, ils sont gardés, alors que les renvoyer écraserait un temps publié par le juge entre la lecture et l'écriture).
  - DQ : `statut` 1 + `complement` (le code, ex. « 12 ») → `statutLabel` « DQ », `isDisqualifie` vrai ; `disqualificationCode` reste `null`.
  - **Un `tempsLiveN` envoyé vide devient `0`**, pas `null` : lire 0 comme « pas de chrono ».
  - **`complement` ne s'efface pas** : vide ou omis, il garde sa valeur (« 12 » resté après retour au statut 0). Une DQ annulée laisse donc son code dans `complement` ; ne l'afficher que si le statut est DQ. À signaler au développeur de l'API.
  - **Jeton invalide à l'écriture → HTTP 403** (vu avec un jeton littéralement faux).
  - Côté PowerShell 5.1, `ConvertFrom-Json` échoue sur ces réponses (clés `id`/`Id` dans le même objet) : lire le texte brut.
- **Non vérifié, connexion par formulaire** : `requestToken` est envoyé avec identifiant et mot de passe dans un corps de formulaire (`application/x-www-form-urlencoded`), non dans l'adresse, comme `FfssApiClient.RequestTokenAsync` de V3. À confirmer sur une vraie connexion ; la v1 les passait dans l'adresse.
- **Non vérifié, lignes de `competition/serie/:id`** : `getHeatResults` et `getHeatChronos` lisent `data.resultats[]` et y attendent `Temps`, `Statut`, `complement`, `TempsLive1..3` et `engagement.id`, comme `resultat/:id`. Que les lignes de la série portent bien ces champs n'est pas confirmé sur la recette ; une ligne illisible est écartée seule, et un `Temps` présent mais illisible vaut « validé ».


## Résultats, vérifié le 2026-10-18 sur la recette 1416 (GET seulement)

- **`GET serie?epreuve=:id`** → `{success, count, data: [{Id, Numero, Nom, Debut, Fin, Fini, UpdatedAt, epreuve: {Id, IdEvenement, IdDiscipline, Genre, genreLabel, discipline, categories}, resultats: [{Id, isValid, Statut, statutLabel, isDisqualifie, Rang, Temps, tempsLabel, TempsLive1..3, points, complement, complementLabel, Athletes, engagement}]}]}`. `Debut`, `Fin` et `Fini` sont `null` pour les séries jamais nagées.
- **`GET epreuve?evenement=:id`** → `{success, count, data: [{Id, IdEvenement, IdDiscipline, Genre, genreLabel, discipline: {Id, Nom, Specialite, Distance, NbAthleteParEquipe, label, specialiteLabel}, categories: [{Id, Nom, NomEn, Relais, label}]}]}` : une épreuve par catégorie. `Specialite` : 2 eau plate, 1 côtier.
- **`GET competition/evenement/:id/participants`** → `{success, data: [{Id, Prenom, Nom, isLicencie, isInvite, Sexe, nationaliteCode, idClub, clubLabel, isValid, categories, engagements: [{id, categorie, epreuve}]}]}`. Ni `participants` ni les engagements ne portent de place (couloir) ni de dossard.
- **Le `Rang` d'un résultat de V3 est la place dans la série pour la catégorie**, pas un rang d'épreuve. **Les points ne sont pas envoyés** : l'app les calcule (barème de V3).
- **`serie?epreuve=` sert des données personnelles sans jeton** : l'objet `Licencie` des athlètes (e-mail, date de naissance). Ne pas les lire ni les copier dans les fixtures.
- **Les vieilles séries restent sur le site** : une épreuve peut en porter qui n'ont plus de course au programme (`Debut` nul).

## Mon espace, vérifié le 2026-10-18 sur la recette (compte de test, GET seulement)

- **`evenement/:id/me` détaille les rôles** : `licencie {id, nom, prenom}`, `officiel {id, niveau, niveauLabel, principal}`, `referent_sportif [{id, label, sigle, nom}]` (un objet par club dont le compte est référent). Les codes de rôle sont aussi dans `roles`.
- **Même numérotation des clubs partout** : l'`id` d'un `referent_sportif` de `/me`, l'`idClub` des participants et l'id des `organismes` désignent le même club. L'app rattache donc un club référent à ses participants par cet id.
- **Un rôle `licencie` ne dit pas que le compte est engagé** : le licencié de `/me` peut être absent des participants de la compétition. Seule la liste des participants (`licencie.id` contre l'id du participant) le dit.
- **`competition/evenement/:id/officiels`** → liste d'officiels avec un niveau (`A`, `B`, `C`, parfois vide), un indicateur de juge principal, les jours où ils officient et leur club. Les champs personnels ne sont **pas lus** : l'app ne garde que nom, niveau, principal, jours et club.
- **Aucun champ `forfait` sur la lecture des engagements**, contrairement à la doc : un forfait déclaré avant la course n'est lisible que par les places (statut, `complement`). Lot 6b.
- **`evenement/:id` publie les contacts de l'organisateur** (téléphone, e-mail). L'app ne les lit pas et les DTO ne les déclarent pas.
